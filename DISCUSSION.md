# Items to Defend

Every decision a reviewer is likely to poke at, the short answer, and the nuance that makes it
a real answer instead of a slogan. Ordered roughly by how likely it is to come up.

---

## 1. "We're a Java shop. Why Go?"

This is the one to get right, and the way to get it wrong is to argue Go is *better*. It isn't;
it was the right pick for *this artifact under this constraint*.

**The honest reason, stated first:** I write Go backends continuously. In a 4-hour time box you
see my best work rather than my rustiest. That is a real engineering consideration for a
time-boxed exercise and pretending otherwise is worse than saying it.

**Three reasons specific to this challenge:**

- **The deploy pipeline is image-size sensitive.** My deploy is `docker build` → `docker save`
  → `scp` → `docker load`. A static Go binary on distroless is ~20MB; a JVM image is 200–400MB.
  That difference is wall-clock on every single deploy over SSH. For a k8s cluster with a warm
  registry it would not matter — for this pipeline it does.
- **Startup and footprint** — modest, real, and I would not lead with it.

That is two reasons, and it used to be three. I had "Go keeps the SQL visible via sqlc, where
JPA buries it in annotations" — but **sqlc has a Java plugin** (beta), so that is an argument
against ORMs, not an argument for Go, and it belongs in §2. Dropping it leaves a shorter list
that actually holds. Two real reasons beat three where one falls over under the first question.

**What I will NOT claim, because a Java engineer will call it:**

- **Not concurrency.** Goroutines-vs-threads was a strong argument until Loom. Virtual threads
  went GA in Java 21 and this workload is IO-bound, which is precisely the case Loom closes.
  Anyone who leads with "goroutines" in 2026 is quoting a 2015 blog post.
- **Not ecosystem.** Spring Boot + Spring Security + Flyway + Testcontainers is more mature
  than any Go equivalent. Spring Security would have given me JWT plumbing and method-level
  authorization essentially free; in Go I hand-rolled both.
- **Not the type system.** Records, sealed interfaces, and pattern matching model this domain
  more precisely than Go structs and a `role string` with a check constraint.

**The point to concede unprompted:** in a Java org, a Go service is an operational outlier —
another toolchain, another base image, another CVE scanning path, a smaller pool of people who
can be paged for it. That is a legitimate reason for a company to say no, and it has nothing to
do with the language's merits.

**Close with:** I would write this in Java on your team without complaint, and I am happy to
walk through what the Spring Boot version of this schema and authorization layer looks like.

## 2. "Why sqlc instead of `database/sql` or an ORM?"

**The usual argument is the weak one.** People pick sqlc to avoid writing `rows.Scan`
boilerplate. That argument is much weaker now — an LLM writes scan code fine.

**The argument that survives:** sqlc gives **compile-time verification against the real
schema**. Rename a column in a migration, regenerate, and the *build* breaks at every query
that touched it. Hand-written `database/sql` — whether typed by me or generated by a model —
fails at *runtime*, in whichever endpoint I forgot to update, possibly in production. On a
project where the schema *is* the design, I want the compiler holding that edge.

**Where sqlc does not fit, and what I did about it:** `GET /v1/notes` has optional filters
(`q`, `tag`, cursor, sort mode). sqlc handles dynamic predicates badly — the `sqlc.narg` +
`WHERE ($1::text IS NULL OR ...)` pattern works but reliably produces bad query plans, because
the planner cannot use an index through the OR-null. So that one query is **hand-written
against pgx**, in its own file, commented as a deliberate exception.

Knowing where your tool stops fitting and stepping outside it explicitly is a better signal
than forcing every query through one mechanism.

**Driver:** pgx/v5 with `pgxpool`, using sqlc's pgx output — not `database/sql`. pgx handles
`text[]`, `tsvector`, `uuid`, and `timestamptz` natively instead of through wrapper types.

**Generated code is committed**, so a reviewer can read it without running codegen.

**This is a language-independent argument.** sqlc has a Java plugin (beta), so the real position
is *sqlc over JPA/Hibernate*, not *Go over Java*. The reason holds either way: on a project
whose substance is an authorization predicate, I want that predicate on the page as SQL, not
distributed across annotations, fetch strategies, and lazy-loading semantics. If the answer to
"why not Java" were only "because sqlc," the honest response would be to write it in Java.

## 3. "Why not just store images in Postgres?"

**Concede the technically correct part first, because it is correct:** values over ~2KB get
TOASTed — compressed and moved out-of-line into a separate relation, with an 18-byte pointer
left in the main heap tuple. So a sequential scan over `notes` does *not* drag the blobs
through memory unless the column is selected. The "big columns slow every query" folk wisdom
is wrong, and I would not use it as the reason.

**The reasons that actually hold:**

1. **WAL amplification** — the strongest one. Every write of a TOASTed value writes all its
   chunks to the write-ahead log. A 50MB video is 50MB+ of WAL, which becomes replication lag,
   larger PITR archives, and slower backups. The cost lands on the parts of the system furthest
   from the feature.
2. **Backup and restore scale with media volume.** Restoring a 500GB database that is 480GB of
   images is a bad afternoon, and it is an afternoon that recurs on every replica rebuild.
3. **Bytes on the app request path.** The upload holds an HTTP connection, a pooled DB
   connection, and app memory for its whole duration. A long transaction also blocks vacuum.
   A video upload over flaky mobile can hold that open for minutes.
4. **No range requests, no CDN.** Video seeking is HTTP range requests, which is native to
   S3+CloudFront and hand-rolled over `bytea`.
5. **1GB hard field limit.**

**Where the instinct is right, and I would say so:** for *small* attachments — screenshots,
diagrams, avatars, under ~1MB — `bytea` is genuinely defensible and **simpler in a way that
matters**, because it buys atomicity. The attachment and the note commit in one transaction.
Every complication in §7 of the spec evaporates: no `pending` status, no orphan sweep, no
two-phase upload, no presign TTL, no revoke gap.

So the real rule is a **threshold on size and media type, not a dogma**: images under a megabyte
in Postgres is a reasonable engineering call; video never is. Assumption A2 includes video, so
object storage wins *here* — but the reasoning is the answer, not the conclusion.

**Disclosure:** I have always built the object-storage path and have not implemented the
`bytea` one in production, so I am reasoning from the mechanics rather than from scar tissue.

## 4. "How do two people edit the same note?"

Three tiers. We build tier 1 and make tier 2 additive.

**Tier 1 — optimistic concurrency (built).** `notes.version` increments on write, returned as
an `ETag`, required back as `If-Match`. The update is one conditional statement — `UPDATE ...
WHERE id = $1 AND version = $2` — so check and write are atomic with no explicit lock. Zero
rows affected means someone else won; return 409 with the current representation so the client
can show a diff rather than just an error.

This is the minimum bar. The moment two people can edit one note, last-write-wins silently
destroys work, and most submissions to this kind of challenge ship exactly that.

**Known limitation, worth raising before they do:** versioning is per-note, not per-field. If
one person edits tags while another edits the body, they get a spurious 409 despite no real
conflict. The fix is a server-side three-way merge when the changed field sets are disjoint —
but that requires knowing the *base* version's values, which means version history, which we
cut. So this limitation and the "add version history" follow-up are the same item, and I would
say that explicitly rather than listing them as two unrelated gaps.

**Tier 2 — presence and live invalidation.** Not concurrent editing; just "this note changed,
refetch." SSE is enough and is far simpler than WebSockets for one-way fanout. The real backend
change is **cross-instance fanout**: with more than one instance, the writer and the listener
are on different processes.

- **Postgres `LISTEN`/`NOTIFY`** — zero new infrastructure, which is the appeal. Caveats worth
  knowing: 8000-byte payload cap, and it needs a dedicated long-lived connection per listener,
  which conflicts with PgBouncer in transaction-pooling mode.
- **Redis pub/sub** — the standard answer, one more thing to run.

With pub/sub fanout you do **not** need sticky sessions, which is the thing people assume.

**Tier 3 — true concurrent editing.** Either OT (server-authoritative, transforms concurrent
ops, what Google Docs does, genuinely hard to get right) or CRDT (Yjs/Automerge — merge is
commutative, so the server can be a dumb relay plus persistence). CRDT is far easier to make
*correct*.

**The part people miss, and the reason I would not call this a bolt-on:** with a CRDT the note
body stops being a queryable text column. It becomes an opaque binary doc plus an update log.
Full-text search then needs a plaintext projection materialized on write, so the tsvector in §3
still works but is now downstream of a merge step rather than the source of truth. `version`
becomes a state vector, `If-Match` stops meaning anything for the body (still fine for title and
tags), the update log grows monotonically and needs compaction, and per-note storage goes from
kilobytes to tens of kilobytes. The payoff is that offline editing comes free.

Tier 3 is a rewrite of the note-body storage path. Saying that plainly is worth more than
claiming it drops in.

## 5. "Where's your rate limiting?"

**First, a precision fix on the usual framing.** "In-process rate limiting means you can't
scale out" is not quite right, and the imprecision is worth correcting because it hides the
real distinction. You *can* scale out fine — what degrades is **accuracy**. With N instances
and a per-user limit of R, the effective limit is N×R and it wobbles with routing.

The useful split is by *what is being protected*:

- **Fairness / quota** ("your plan allows 100 req/min") — protects a *shared* resource, so it
  needs shared state. Redis token bucket, or enforced at the API gateway. In-process is simply
  wrong here.
- **Self-protection** (don't exhaust this process's memory or its DB pool) — protects a *local*
  resource, so it needs no coordination at all. **In-process is the correct place**, not a
  compromise.

So "rate limiting belongs at the edge" is half true. The layered answer:

| Layer | Enforces | Where |
|---|---|---|
| Volumetric / DDoS | Gross request floods | CloudFront / WAF / ALB |
| Per-tenant quota | Business policy | API gateway, or Redis token bucket |
| Per-instance concurrency + pool caps | Instance survival | In-process |

**What ships:** rate limiting proper is **out of scope**, documented with the above. What *does*
ship are the in-process pieces that are correctness concerns rather than policy, and cost about
twenty lines total: max request body size, server read/write/idle timeouts, bounded `pgxpool`,
and the attachment size cap enforced at presign.

Being able to say precisely what you would build and why you did not build it is a better
answer here than an unconfigurable token bucket nobody asked for.

**One consequence to name rather than let someone find:** deferring rate limiting leaves
`POST /v1/auth/login` open to password brute force. That is not really a rate-limiting problem —
it is an authentication problem that happens to share a mechanism, and it is not solved at the
edge, because a WAF cannot tell a failed login from a successful one. The right fix is
failed-attempt throttling keyed on account plus source, with backoff, which needs shared state.
It is a genuine gap in this build and it is the first thing I would add.

## 6. "Your attachment size limit — can you actually enforce it?"

Worth pre-empting, because the obvious implementation does not work.

**A presigned PUT cannot enforce object size.** The signature covers the key and headers, not
the body length. A client handed a presigned PUT URL can upload any number of bytes.

Three ways to actually enforce it:

1. **Presigned POST with a policy document** — supports `content-length-range`, and S3 rejects
   the upload itself. The correct answer, slightly more fiddly on the client.
2. **Verify at `/complete`** — `HEAD` the object, compare against the declared `size_bytes`,
   delete and reject on mismatch. Simple, but the bytes were already paid for.
3. **Bucket policy / lifecycle** as a backstop.

We do (2) with (1) named as the upgrade. The point is knowing the presigned PUT gap exists —
a size check that lives only in the presign request handler is decorative.

## 7. "What happens when you delete a user or a team?"

This is where the polymorphic ACL bites, and I would rather raise it than have it found.

`note_shares.principal_id` is **not a foreign key** — it points at either `users` or `teams`
depending on `principal_type`, and Postgres cannot express that. So `ON DELETE CASCADE` does
not save us:

- **Deleting a team** leaves orphaned `('team', id)` share rows. If that UUID were ever reused,
  they would grant access to the wrong principal. Team deletion must explicitly delete matching
  shares **in the same transaction**.
- **Deleting a user** has the same problem for `('user', id)` rows.

Both get an integration test. This is the concrete price of the one-table ACL, and the
alternative — two nullable FK columns plus a check constraint that exactly one is set — buys
real referential integrity for a slightly clumsier schema. I would call that a coin flip and
defend either, which is a more honest position than insisting the polymorphic version is free.

**Deleting a user is also a product decision, not just a schema one.** Hard-deleting someone's
notes destroys other people's working context in a *shared* notes service — the notes are not
only theirs anymore. So: soft-delete the user, notes survive, the owner renders as a tombstone,
tokens are revoked. GDPR erasure would need a separate anonymize-and-retain path, which is
noted rather than built.

**Related, and security-relevant:** to share a note with someone you must first find them. A
general user-directory search is a data-harvesting surface, so lookup is **exact-match on email
only**, and scoped to users who share a team with the caller. Enumeration is a real risk and it
costs nothing to close at design time.

**Last-admin protection:** a team's final admin cannot be removed or demoted.

## 8. "Why 404 instead of 403?"

When the caller cannot read the note at all, the response is 404. A 403 confirms the note
exists, which turns ID enumeration into a way to learn about other teams' data.

403 is reserved for the case where the caller *can* read the note but lacks the role for the
specific action — the existence is already known to them, so there is nothing left to leak.

## 9. "Why no partitioning?"

Because a note can be shared with two teams, there is no partition key that keeps a note and
all its ACL rows co-located. Team-partitioning would make exactly the cross-team queries the
product is built around fan out across partitions — it would add cost and *remove* the benefit.

Volume also does not justify it; "several small teams" is not a partitioning problem.

The trigger to revisit is sustained single-table volume where index maintenance or vacuum
becomes the bottleneck — and at that point the partition key is **time** (`created_at`), not
team, because time-partitioning is orthogonal to the sharing model and team-partitioning is
actively hostile to it.

**Row-level security** was also considered and rejected: it moves authorization out of testable
application code and into policies that are harder to unit test and harder to explain in a code
review. It is a good defense-in-depth layer for a higher-assurance deployment, on top of the
application rules rather than instead of them.

## 10. "How is this tested?"

**Graded suite: standard `go test`.** Table-driven unit tests over the full role × action ×
principal-type matrix — that is the code where a bug is a data leak, so it gets exhaustive
coverage. Integration tests run against real Postgres and real MinIO in Docker, no mocked
database, because every interesting bug here lives in a SQL predicate.

**Deliberately not using an external test runner for the graded suite.** A reviewer should be
able to clone and run `go test ./...`. Requiring a separate tool to run the tests is friction
that costs more than the tool adds.

**Multi-user flows are part of the plan, not a stretch goal.** A `flows/` directory, using the
request-flow pattern from my project template — several authenticated clients driving the API
against each other. This domain demands it: the authorization rules are only interesting with
more than one user in play, and a single-client test cannot express "Bob cannot see Alice's
private note." In-repo Go, no external dependency, and the same binary is what `smoke.sh` runs
against a deployed environment.

**The behavior list and the test list are the same document.** CAPABILITIES.md marks each row
`unit`, `flow`, `int`, or `—`. That is deliberate: a capability matrix that is not the test
manifest drifts from reality within a week, and a test suite with no behavior list has no way to
show what it does *not* cover. The `—` rows are the scope boundary, visible rather than absent.

**On noCRUD specifically:** its Go implementation is README-only right now — the repo's own
README says the Python implementation is far more advanced and the Go MVP is not yet
transferred. So testing this service with noCRUD would mean writing noCRUD's Go MVP first,
which does not fit the budget. The genuinely interesting experiment — pointing the *Python*
runner at a non-Django backend — is a real test of how much Django convention is baked into its
auth and URL handling (its client currently assumes `/token/`, trailing slashes, and an
`{"access": ...}` response shape). Worth doing, on its own time, not on the takehome clock.

## 11. "How would you deploy this?"

Target topology, documented rather than built:

- **Compute** — single host behind Traefik for TLS termination and routing. Deploy is `docker
  build` → `docker save` → `scp` → `docker load` → `docker compose up -d`, the pattern from my
  project template. Provisioned by Terraform.
- **Database** — RDS Postgres. Locally it is Postgres in compose; the only difference is a
  connection string.
- **Object storage** — real S3 in production, MinIO in compose. This is precisely why storage
  sits behind an interface: it is a one-line swap, and the presigned-URL flow is identical
  because MinIO is S3-compatible.
- **Secrets** — currently `pass` on the dev machine generating a `.env_prod` that is scp'd over.
  Honest about the ceiling on that: it puts production secrets on a laptop and in a transferred
  file. The upgrade is SSM Parameter Store or Secrets Manager with an IAM-scoped instance role,
  so secrets are never at rest outside AWS. Out of scope, named in the README.

The single host is a deliberate match to the stated scale. Nothing in the design prevents
running several instances behind a load balancer — the service is stateless, sessions are JWTs,
and the only coordination point would be the SSE fanout in §4, which is exactly why that section
specifies pub/sub rather than in-process hub state.

**Two release decisions worth defending separately** (mechanics in SPEC §12):

- **Migrations never run on app startup.** With N instances they race for the same database, and
  a self-migrating app cannot be rolled back — the old binary would come back up against a
  schema it does not understand. So: a discrete step, before the new version starts, with
  expand/contract for anything that must not break the version still serving traffic.
- **Bash, not GitHub Actions.** A reviewer can read a forty-line shell script and know exactly
  what happens; a workflow file they cannot run demonstrates YAML, not deployment. The honest
  cost is no audit trail and dependence on local state. The upgrade is *these same scripts,
  invoked by CI* — which is the argument for putting the logic in scripts even once you have CI,
  rather than dissolving it into workflow steps.

## 12. "Why is observability in scope when rate limiting isn't?"

A fair scope-coherence challenge, and the answer is a single consistent rule rather than two ad
hoc calls.

**Rate limiting protects a shared resource and belongs where the shared view is** — the edge, or
a shared store. Implementing it in-process produces a limit that is wrong by a factor of N and
duplicates something the infrastructure already does better.

**Observability describes what this process did, and nothing else can produce it.** No gateway
knows which route pattern was matched, which user made the call, or why a request took 800ms.
Push it outward and you get status codes and nothing else.

The rule: **build what only this service can know; delegate what a shared layer knows better.**
That is also why in-process *limits* do ship — body caps, timeouts, pool bounds — since those
protect this process's own memory and connections, which no edge can see.

The same rule explains the one exception worth flagging: login brute-force throttling looks like
rate limiting but is not delegable, because the edge cannot tell a failed login from a
successful one. Only this service knows. By the rule above it should have been built, and it is
the sharpest gap in the current scope.

## 13. "Your pool is bounded at ten. What happens to request eleven?"

It waits — and until recently, it waited forever. Working through that question is what
produced the request deadline, so it is worth tracing properly.

`net/http` gives every request its own goroutine, and Go will happily make thousands of them.
A Postgres connection executes exactly one query at a time, so concurrent queries need
concurrent connections. `DB_MAX_CONNS` (10) is where those two facts meet: at most ten queries
run at once, and goroutine eleven parks inside `pgxpool` until one frees up.

Ten sounds small until you notice **when** the connection is held. It is acquired at the query
and released the moment it returns — not for the life of the request. Parsing, authorization,
serialization and the response write all happen without one. Since the database is a small
slice of each request, ten connections comfortably serve far more than ten concurrent users.
The exception is a transaction, which holds its connection from `Begin` to `Commit`: long
transactions exhaust this pool in a way high request volume does not.

**The bug that analysis surfaced.** A parked goroutine waits on its context. The server's
`WriteTimeout` does *not* cancel the request context — it is a deadline on the socket, and Go
cancels a request context only when the client disconnects or the handler returns. So the pool
bounded connections correctly while the queue of waiters behind it had no bound at all. Under
sustained overload that queue grows until the process does, and the 60s write timeout quietly
abandons sockets whose handlers keep waiting for clients that are already gone.

**What ships:** `REQUEST_TIMEOUT` (15s, validated below the write timeout) as a context
deadline in `obs.Timeout`. It cancels rather than pre-empts — the deadline unblocks anything
context-aware, pgx included, which returns `context.DeadlineExceeded`, which `httpx.WriteProblem`
renders as a 503. `http.TimeoutHandler` would guarantee a response even from a handler that
ignores its context, but it writes its own plain-text body, putting one response outside the
problem+json contract every other error obeys. Cancellation covers every path this service
actually has.

**Two errors stopped being 500s**, which matters more than it sounds. A deadline and a client
disconnect both reach the error path as context errors, and both were being logged as
"unhandled error" and served as 500. Shed load is now a 503 logged at warn; a disconnect is a
499 logged at info with no body, because there is no one left to write to. The 500 bucket is
what an on-call alert watches, and it should mean "this service has a bug" — not "someone
closed a laptop."

**And it is now visible.** `pgxpool_*` exports the pool's own counters, which is the only way
to tell "the query was slow" from "the request waited its turn" — opposite fixes, identical
latency graph. The number to watch is `pgxpool_acquire_wait_seconds_total` over
`pgxpool_acquires_total`: average time queueing rather than working.

`pgxpool_acquires_empty_total` is the trap. It reads like a saturation counter, but pgxpool
increments it whenever an acquire finds no *idle* connection — including while the pool is
still growing toward its ceiling. With `MinConns` at 0 a healthy cold pool records one per
connection it opens. It means saturation only alongside `pgxpool_connections{state="acquired"}`
sitting at `pgxpool_connections_max`. That was mis-documented here first, and the test caught it.

**Where this goes next.** The whole arrangement holds because there is one long-lived process:
a client-side pool *is* the pooler, and RDS ships no pooler of its own. The trigger for adding
one — RDS Proxy, or PgBouncer — is process count, not traffic. Every additional instance brings
its own pool and the database sees the sum, which is also the real reason Lambda would be a poor
fit here: a function container holds its connection for the container's lifetime, idle time
included, so connections would scale with concurrency instead of with query time.
